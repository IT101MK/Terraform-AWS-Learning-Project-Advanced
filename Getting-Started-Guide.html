1 What you're building

A small fleet, not a single server — the difference between "a Terraform apply" and "operating infrastructure."

Lab / learning project only — not production-ready. Everything here is built for short-lived lab testing in a personal AWS account and destroyed at the end of each session. The hosts sit in a public subnet and serve a demo page over plain HTTP (port 80, no TLS) to the whole internet; one IAM role is shared across the fleet; the data bucket uses force_destroy. These are deliberate simplifications for learning and cost, not safe defaults. Review and harden anything before reusing it — see What to learn next.

This project is the advanced companion to the base Project-IaC build. Instead of one EC2 instance, it provisions a fleet of host_count identical hosts through a reusable Terraform module (a self-contained group of resources you call once per host with different inputs, instead of copy-pasting the same block host_count times), monitors them with CloudWatch, manages them with Ansible over SSM (no SSH keys anywhere), and ships a small telemetry payload from each host into a lifecycle-managed S3 bucket — deliberately modelled on capturing readings from remote assets and centralising them into one data store. A separate, isolated component briefly stands up a real AWS Managed Microsoft AD directory for a portfolio screenshot.

Two terms this guide uses constantly: state and backend. Terraform's state is the file it uses to record what it has already created, so the next plan/apply knows what's already there instead of starting from scratch. A backend is just where that state file is stored — on your own disk by default, or somewhere shared (like the S3 bucket bootstrap/ creates in Stage 0) so state isn't stranded on one machine. Both terms come up repeatedly from here on.

3 Prerequisites

Everything from the base Project-IaC prerequisites, plus what this project's extra layers need.

  • AWS account, IAM user, budget alert, AWS CLI, Terraform — same as the base project. If you haven't done that setup yet, do it first.
  • Terraform 1.10.0 or later — backend.hcl turns on use_lockfile = true (native S3 state locking, which stops two concurrent applys from writing to the same state file at once), a Terraform 1.10 feature. Older versions don't understand the argument at all.
  • AWS Session Manager plugin (Windows) — aws ssm start-session run from a plain Windows PowerShell/CLI session shells out to this local binary: winget install -e --id Amazon.SessionManagerPlugin
  • AWS Session Manager plugin (WSL, separate install) — the Windows plugin above does not cover Ansible. The aws_ssm connection plugin runs inside WSL's own Linux environment and needs its own Linux build of the same plugin, or the baseline/telemetry playbooks fail immediately on Gathering Facts.
  • Python 3 with boto3/botocore — required underneath the amazon.aws Ansible collection: winget install Python.Python.3.12, then pip install boto3 botocore
  • Ansible (ansible-core) — run it from WSL, a Linux VM, or macOS. Ansible does not support a native Windows control node; PowerShell alone won't run ansible-playbook.
  • AWS credentials inside WSL — WSL keeps its own ~/.aws/, separate from Windows' %USERPROFILE%\.aws\. Copy or share your credentials into WSL, or every Ansible command fails with Unable to locate credentials even though the Windows-side AWS CLI works fine.
  • PowerShell AWS Tools modules for Get-FleetHealth.ps1 — see the install command in section 10.

Install commands (PowerShell, run as Administrator where noted)

# --- Terraform (upgrade if you're still on the base project's older pin) ---
winget install Hashicorp.Terraform
terraform version   # confirm 1.10.0 or later

# --- Session Manager plugin (Windows side) ---
winget install -e --id Amazon.SessionManagerPlugin
session-manager-plugin   # prints version info if installed correctly

# --- Python for the Ansible collections ---
winget install Python.Python.3.12
pip install boto3 botocore
Warning: Ansible does not run as a Windows control node. Install and run ansible-core from WSL (wsl --install if you don't already have it), a Linux VM, or macOS — not directly from PowerShell. Terraform and the PowerShell health script both run fine natively on Windows; only the Ansible layer needs a POSIX environment.

Inside WSL: the two gotchas that only show up there

# --- Session Manager plugin, Linux build (separate from the Windows one above) ---
curl "https://s3.amazonaws.com/session-manager-downloads/plugin/latest/ubuntu_64bit/session-manager-plugin.deb" -o "session-manager-plugin.deb"
sudo dpkg -i session-manager-plugin.deb

# --- AWS credentials: WSL has its own ~/.aws/, distinct from Windows' ---
mkdir -p ~/.aws
cp /mnt/c/Users/<you>/.aws/credentials /mnt/c/Users/<you>/.aws/config ~/.aws/
Warning: skipping either of these fails silently until you run a playbook. Without the Linux plugin, ansible-playbook fails immediately on Gathering Facts with Failed to find required executable "session-manager-plugin". Without WSL's own credentials, it fails with Unable to locate credentials — even though aws sts get-caller-identity works fine on the Windows side. Both are one-time setup steps, not per-session ones.

5 Stage 0: remote state bootstrap

bootstrap/ — applied once, ever. Not part of the destroy-every-session cycle.

Note: why this can't use the backend it creates. Classic chicken-and-egg problem: the root project's state lives in an S3 bucket, but something has to create that bucket before Terraform can point a backend at it. bootstrap/ breaks the cycle by keeping its own state locally (bootstrap/terraform.tfstate, gitignored) permanently.
5.1

Apply the bootstrap config

cd bootstrap
terraform init
terraform apply
terraform output state_bucket_name

Copy the bucket name from the output — you'll need it in the next stage. Expect Plan: 6 to add.

5.2

Understand what it created

An S3 bucket (versioned, SSE-S3 encrypted — S3's own server-side encryption, no separate key to manage — all public access blocked) — this is what actually holds state for the root project and ad-demo/, at different keys within the same bucket.

A DynamoDB table, included for reference only. This is the "classic" Terraform locking pattern — a table holding a lock item while an apply is in progress, standard for years and still what you'll find in most existing Terraform codebases. Neither of this project's actual configs uses it: they use Terraform's native S3 locking instead (use_lockfile = true, a conditional-write lock file inside the state bucket itself, Terraform ≥ 1.10). Both solve the same problem; the table is here purely so the older pattern is visible in the repo.

6 Stage 1: multi-host fleet, module, and remote state

Back in the project root. This is where the fleet — and its reusable module — comes together.

6.1

Point the backend at Stage 0's bucket

backend.tf declares an intentionally empty s3 backend block — "partial configuration." The real bucket name (random suffix, different per account) is supplied separately at init time rather than hardcoded into a committed file:

cd ..   # back to the project root
Copy-Item backend.hcl.example backend.hcl
notepad backend.hcl   # paste in state_bucket_name from Stage 0's output
terraform init -backend-config=backend.hcl

backend.hcl also sets use_lockfile = true — native S3 locking. No DynamoDB table is referenced from here.

6.2

The host module

hosts.tf decides how many hosts to create and what's unique about each one; modules/host/ knows nothing about the rest of the project — it just launches one instance from whatever inputs it's given.

Module inputWhere it comes from
ami_idAMI data source in hosts.tf (latest Amazon Linux 2023)
instance_type, root_volume_gbRoot variables.tf
subnet_id, security_group_ids, iam_instance_profileShared resources from network.tf / iam.tf
key_namekey_pair_name variable (optional, null by default)
user_datatemplatefile() over user_data.sh.tpl, with a per-host host_key
name_tag"${project_name}-host-${host_key}"
Module outputUsed for
instance_idCloudWatch alarm dimensions, host_instance_ids output, SSM targeting
public_iphost_public_ips output, SSH command construction
private_ipAvailable if you need it (not currently used elsewhere in this config)
Note: for_each, not count. Terraform offers two ways to create multiple copies of the same resource block: count (indexed 0, 1, 2...) and for_each (keyed by a string or map you provide). With count, removing host 1 out of 3 shifts host 2 into index 1's slot — Terraform sees that as "destroy the old index 1, create a new index 1," cascading through every host after the one you removed. This project uses for_each = toset(local.host_keys) instead, with string keys like "01", "02" — there's no index to shift, so removing a host from the middle of the fleet destroys only that host, not every host after it. See the troubleshooting table for what this does and doesn't protect you from.
6.3

Plan and apply

terraform fmt
terraform validate
terraform plan    # default host_count = 2
terraform apply

With the default host_count = 2, the full plan across every stage in this root config (network + storage + IAM + hosts + monitoring) is Plan: 21 to add, 0 to change, 0 to destroy.

7 Stage 2: SSM + CloudWatch monitoring

Same root apply as Stage 1 — monitoring.tf lives alongside hosts.tf, not in a separate directory.

SSM Session Manager is the primary way to reach these hosts, not a fallback. ssh_allowed_cidr defaults to null, and the security group's SSH rule — a dynamic "ingress" block — simply doesn't exist unless you set it:

aws ssm start-session --target <instance-id>   # works with no key pair and no open port 22

monitoring.tf adds, per host, a StatusCheckFailed alarm (AWS's own instance/system health check) and a CPUUtilization alarm (threshold from cpu_alarm_threshold, default 80%). Both feed one CloudWatch dashboard for the whole fleet:

terraform output dashboard_url
Tip: alarm notifications are opt-in. Alarms exist and show up in the console either way. Set enable_alarm_notifications = true and an alarm_email in terraform.tfvars if you actually want to be paged — you'll need to confirm the SNS subscription email AWS sends you.

8 Stage 3: Ansible configuration management

ansible/ — no SSH key anywhere in this layer, no static inventory file, no bastion host (a public jump box you'd otherwise SSH into first to reach hosts in a private network — SSM replaces the need for one here).

8.1

Install collections and set the bucket name

# from WSL/Linux — ansible-core does not run as a Windows control node
cd ansible
ansible-galaxy collection install -r requirements.yml

Edit group_vars/all.yml and set s3_bucket_name to the real bucket name from terraform output bucket_name. It ships as a placeholder, CHANGE_ME-set-from-terraform-output — every module Ansible runs, not just file transfers, is relayed through this bucket, so the aws_ssm connection fails outright until it's set.

8.2

Confirm the dynamic inventory, then run the baseline

inventory/aws_ec2.yml asks AWS, on every run, which instances are tagged Project: terraform-advanced and currently running — there's no static host list to keep in sync by hand. Terraform is the single source of truth for which hosts exist.

ansible-inventory --graph                       # confirm the fleet is discovered
ansible-playbook playbook.yml --tags baseline

The baseline tag: refreshes and fully updates dnf packages, installs dnf-automatic for unattended patching between playbook runs (applies updates, never auto-reboots — an unannounced reboot is exactly what an OT-flavoured environment wants to avoid), (re)installs nginx and deploys a fleet status page identically to every host, disables SSH password authentication as defense-in-depth, and confirms the SSM Agent service is active.

9 Stage 4: S3 telemetry/backup pipeline

Directly analogous to capturing field data and transferring it into a centralised library.

9.1

Deploy the telemetry pipeline

ansible-playbook playbook.yml --tags telemetry

The telemetry tag deploys telemetry-upload.sh (templated with the bucket name and region baked in), a systemd oneshot service, and a systemd timer — not cron, so the schedule shows up in the same systemctl/journalctl tooling as every other service on the box. The timer fires every telemetry_interval_minutes (default 15), 2 minutes after boot, with a randomized 30-second delay so a fleet provisioned near-simultaneously doesn't send simultaneous S3 PutObject calls.

Each payload is small: hostname, timestamp, uptime, disk and memory usage, written to s3://<bucket>/telemetry/<hostname>/<timestamp>.json.

9.2

Verify objects are landing, and understand the retention rule

aws s3 ls s3://<bucket-name>/telemetry/ --recursive

On the Terraform side, storage.tf's aws_s3_bucket_lifecycle_configuration expires everything under telemetry/ after 30 days — the retention half of a "data library": telemetry accumulates long enough for analysis without silently growing (and costing) forever.

10 Get-FleetHealth.ps1

A local PowerShell script — runs on your machine, not the instances. Usable from Stage 2 onward.

Install the modules it needs first:

Install-Module -Name AWS.Tools.Installer -Scope CurrentUser
Install-AWSToolsModule AWS.Tools.EC2,AWS.Tools.SimpleSystemsManagement,AWS.Tools.CloudWatch,AWS.Tools.SecurityToken -CleanUp
Note: all four modules are required. The script calls Get-STSCallerIdentity (from AWS.Tools.SecurityToken) as its first sanity check. All four modules are declared in the script's #Requires header, so PowerShell refuses to start it if any of them is missing — install all four, as above.
ParameterDefaultPurpose
-ProjectTagterraform-advancedFilters instances by the Project tag providers.tf sets on everything
-Regionus-east-1Must match the region you actually deployed into
-ReportPath(none)If set, also writes a timestamped .html and .csv report there (created if missing — point it at the gitignored reports/ folder)

.\Get-FleetHealth.ps1 -ReportPath .\reports -Region us-east-1

12 Troubleshooting

Specific causes and fixes, read against the actual code in this repo.

SymptomCauseFix
terraform plan on a host_count change wants to destroy hosts you didn't touch for_each uses string keys ("01", "02"...), so a genuine host_count change only destroys the highest-numbered host(s) removed, plus their 2 alarms each, plus an in-place dashboard update. If the plan shows every host being replaced, the real trigger is usually instance_type, root_volume_gb, or key_pair_name in terraform.tfvars — these propagate identically into every module.host call. Read the plan's per-resource action list before applying. If you didn't mean to replace every host, revert the shared variable you just changed.
SSM console/CLI shows an instance as "Not connected" Most commonly, the SSM Agent hasn't registered yet (give it 1-2 minutes after apply); occasionally, the console is pointed at the wrong region (must match var.aws_region, us-east-1 by default). Wait a couple of minutes, then confirm directly: aws ssm describe-instance-information --region us-east-1. Confirm console and CLI are pointed at the same region.
Ansible reports UNREACHABLE over the aws_ssm connection One of: s3_bucket_name in group_vars/all.yml still has its placeholder value; the local Session Manager plugin isn't installed; boto3/botocore aren't installed in the Python environment ansible-playbook runs from; your own control-machine IAM identity lacks ssm:StartSession — a different permission boundary from the instance role. Fill in s3_bucket_name from terraform output bucket_name; confirm session-manager-plugin is on PATH; pip install boto3 botocore; confirm your local identity can start SSM sessions with aws ssm start-session --target <id> directly.
First terraform init against the S3 backend fails bootstrap/ hasn't been applied yet, backend.hcl still has the placeholder bucket name from backend.hcl.example, or -backend-config=backend.hcl was left off the init command entirely. Apply bootstrap/ first; run terraform output state_bucket_name there and paste the exact value into backend.hcl; always pass -backend-config=backend.hcl; add -reconfigure if a previous partial init left things cached.
CloudWatch alarms stuck in INSUFFICIENT_DATA The status-check alarm needs one full 5-minute datapoint; the CPU alarm needs two consecutive ones (~10 minutes) — a freshly-applied host simply hasn't existed long enough. treat_missing_data differs between them: status_check is "breaching", cpu is "notBreaching". Wait 10-15 minutes after apply before judging alarm state. Confirm the instance is actually running — a stopped instance stops emitting these metrics entirely.
Alarm count approaching the 10-alarm Always-Free ceiling 2 alarms × host_count (capped at 5, so this project alone tops out exactly at 10, not over it) — but other alarms already in the account (another project, or a previous session's leftovers) push the account-wide total higher. Check the account-wide total before raising host_count: aws cloudwatch describe-alarms --region us-east-1 --query "length(MetricAlarms)". Confirm previous sessions were fully destroyed.
Get-FleetHealth.ps1 gets AccessDenied on CloudWatch/SSM calls The script runs as your local IAM identity, not the fleet's shared instance role — separate permission boundary. Run Get-STSCallerIdentity yourself first to confirm which identity the script will use; grant the local identity read access to EC2/CloudWatch/SSM if it's narrower than AdministratorAccess.
ad-demo apply succeeds but sits in Requested/Creating for a long time Expected, not a fault — AWS's own documentation quotes 20-40 minutes to reach Active. Poll with aws ds describe-directories --directory-ids <id> or refresh the console. Only worth investigating if it exceeds roughly an hour or moves to Failed.
ad-demo password rejected by AWS despite passing terraform validate Terraform's validation block matches AWS's real CreateMicrosoftAD rules exactly — there's no gap to fix in the code. The rejection is almost always something Terraform can't see: PowerShell interpreting an unquoted $ before Terraform ever receives the value, stray whitespace pasted into terraform.tfvars, or a shell-mangled special character. Set the password via $env:TF_VAR_directory_password = '...' using single quotes in PowerShell (literal, no interpolation); read the exact InvalidParameterException text in the apply output — it names the specific rule that failed.
terraform init -backend-config=backend.hcl fails in Windows PowerShell 5.1 with Error: Too many command line arguments. Did you mean to use -chdir?, even though the syntax matches Terraform's own docs exactly Windows PowerShell 5.1's native argument parser doesn't hand a single-dash -flag=value argument to terraform.exe the way Terraform expects — a PowerShell-side parsing quirk, not a Terraform bug, and not specific to init: any single-dash -flag=value Terraform invocation hits it from PowerShell 5.1. Prefix the command with PowerShell's stop-parsing token: terraform init --% -backend-config=backend.hcl. Everything after --% is passed through literally. PowerShell 7+ and WSL/Linux shells aren't affected.
From WSL, ansible-inventory --graph silently shows only @ungrouped — no fleet, no obvious error Ansible refuses to auto-load ansible.cfg from the current directory when that directory is world-writable (777) — which is how WSL exposes Windows-mounted /mnt/c/... paths by default. This is a deliberate Ansible safety check, and it only surfaces as a warning buried in the output. Set ANSIBLE_CONFIG explicitly rather than relying on the implicit cwd search — an explicit path bypasses the check (it only blocks the implicit search): ANSIBLE_CONFIG=./ansible.cfg ansible-inventory --graph (same prefix for ansible-playbook).
Get-FleetHealth.ps1 fails on every host with A parameter cannot be found that matches parameter name 'UtcStartTime' The script calls Get-CWMetricStatistic with -StartTime/-EndTime (already UTC — $now is computed via .ToUniversalTime()); an older version of the script used -UtcStartTime/-UtcEndTime, which the currently-installed AWS.Tools.CloudWatch module doesn't expose. Already fixed in the script as written — the parameter names are set by whichever AWS.Tools.CloudWatch version you have installed, not by this repo. If this ever resurfaces against a different AWS.Tools.CloudWatch version, check the real parameter names with Get-Command Get-CWMetricStatistic -Syntax and update the two calls in the script to match.
terraform destroy in bootstrap/ fails with BucketNotEmpty: ... You must delete all versions in the bucket Only relevant if you ever want to fully retire Stage 0 — not the normal per-session flow, where bootstrap/ is left running permanently. bootstrap/main.tf's state bucket deliberately has no force_destroy and versioning enabled (see the comments in that file). As long as it holds the root project's real state file, S3 versioned-bucket deletion requires purging every object version and every delete marker, not just current objects. One-time manual fix: enumerate every version and delete marker with aws s3api list-object-versions --bucket <bucket> and batch-delete them with aws s3api delete-objects --bucket <bucket> --delete file://versions.json, then retry terraform destroy.

Same discipline as the base project, applied to more moving pieces.

  • The fleet's public IPv4 charges and EBS usage are small individually but real, and they add up across a full fleet left running unattended.

15 What to learn next

Deliberately not built here — the natural next rungs.

TopicWhy it matters
Private subnet + VPC Interface EndpointsThis project's hosts sit in a public subnet for simplicity and cost (no NAT Gateway). A locked-down variant would move them to a private subnet and add Interface Endpoints for SSM/S3/CloudWatch so they never need a public IP or a route to the internet at all — a realistic next step for anything OT-adjacent.
HTTPS instead of open port 80The lab serves its status page over plain HTTP to 0.0.0.0/0. A real service would put an Application Load Balancer with an ACM certificate in front, redirect or close port 80, and only allow the load balancer to reach the hosts.
tflint / checkovAutomated linting and security-policy scanning for the .tf files, catching misconfigurations before apply rather than after.
CI running terraform plan on PRsA GitHub Actions workflow that runs fmt -check, validate, and plan on every pull request — the review-before-merge discipline a real team would expect.
Per-host IAM rolesThis project deliberately shares one IAM role across the whole fleet because every host does identical work. A fleet with differentiated roles would want per-host or per-role profiles instead.
Auto Scaling GroupReplacing the fixed for_each fleet with an ASG would add self-healing at the cost of losing the simple, individually-addressable host-01/host-02 naming this project relies on for its walkthrough.
Secrets Manager for the AD demo passworddirectory_password currently lives in an environment variable or a gitignored tfvars file. A team setting would generate and store it in AWS Secrets Manager instead, with Terraform reading it via a data source.
